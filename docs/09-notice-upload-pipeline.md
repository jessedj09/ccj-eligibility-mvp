# 09. 공고 업로드 판정 파이프라인 설계 (초안 v0.1, 2026-10-25)

> 상태: **설계 확정(2026-10-25). P0 구현 완료, P1(T3.1~T3.4) 완료(2026-10-25 — 결과 15·16절)**. P2는 4단계 결정 후. 관련 문서: PRD v2(`기획서/PRD_v2.md`, 로컬) 8.1절,
> 공고 등록 절차 [08-adding-a-notice.md](08-adding-a-notice.md), 규칙 데이터 설계 [06-rule-data-design.md](06-rule-data-design.md).

## 0. 요약

- 사용자가 공고문 PDF를 올리면, **이미 검증된 공고는 바로 판정**하고, 처음 보는 공고는 **"사업 템플릿의 빈칸 채우기 →
  검증 관문 → 판정 엔진"** 순서로 *검증 전 초안* 판정을 만든다.
- 빈칸 채우기는 **결정론 추출기가 먼저**, 남은 빈칸만 **교체 가능한 LLM 슬롯**(없음 / 로컬 Ollama / Claude API)이 채운다.
- 어떤 값이든 **원문 문장·쪽이 원문 PDF에 실제로 있어야** 통과한다. 통과 못 하면 그 조건은 '보류(수동 확인)'로 판정된다 —
  추출이 틀려도 **틀린 "신청 가능"이 나가지 않게** 하는 것이 설계의 중심이다.
- 핵심 자산(사업 템플릿·결정론 추출기·검증 관문·정답 데이터셋)은 우리가 소유하고, LLM은 부품이다 → 11절 "내재화 전략".
- 추가 비용 없는 순서: **P0(등록 공고 인식, LLM 없음) → P1(로컬 Ollama로 등록 보조 + 정확도 측정)** → P2 이후는 측정 결과로 결정.

## 1. 목적과 범위

| 항목 | 내용 |
|---|---|
| 목적 | 주요 기능1 "공고문 업로드 → 내 정보 입력 → 지원 가능 / 불가 / 보류"를 검증 원칙을 지키며 제공 |
| 대상 | LH·SH 공공임대 공고 PDF (HWP는 PDF로 변환 안내) |
| 1차 범위 | 이미 등록된 사업 유형(행복주택·신혼희망타운 행복주택·청년매입임대·신혼·신생아 매입임대Ⅰ·Ⅱ·든든전세·SH 미리내집·장기미임대·장기전세·장기전세2)의 **새 차수 공고** |
| 범위 밖(현 단계) | 처음 보는 사업 유형의 완전 자동 판정, 순위·가점·당첨 계산, 공통 결격사유 판정 |
| 비용 원칙 | 현 단계는 추가 비용 없음. Claude API는 고도화 단계 선택 사항(2026-10-25 결정) |

## 2. 설계 원칙

1. **LLM은 읽기만 한다.** 판정·보류 판단·사유 작성은 지금의 결정론 엔진이 한다(프로젝트 원칙 1번).
2. **모든 값에는 원문 근거.** 값마다 근거 문장과 쪽 번호가 붙고, 그 문장이 그 쪽 PDF 텍스트에 실제로 있어야 한다.
3. **검증 못 하면 보류.** 틀린 판정보다 보류가 낫다. 보류는 "수동 확인 필요"로 사용자에게 보인다.
4. **공고당 한 번만 추출.** 결과를 PDF 지문(sha256)으로 저장해, 같은 공고를 여러 사용자가 올려도 다시 추출하지 않는다.
5. **LLM은 교체 가능한 부품.** 추출기 슬롯의 입출력 계약을 고정해 두고, 어떤 모델이든 같은 정답지로 평가해 고른다.

## 3. 전체 흐름

```
[사용자] 공고 PDF 업로드
   │
   ▼
① 텍스트 추출 ── pypdf, 쪽 단위 (실패 쪽은 빈 쪽으로 기록)
   │
   ▼
② 공고 식별 ── sha256 / 주택관리번호 / 제목+공고일
   ├─ 등록 공고(검증 완료) ─────────────────────────────► ⑦ 판정 (정식)
   ├─ 이전에 자동 추출한 공고(캐시) ─────────────────────► ⑦ 판정 (검증 전 초안)
   └─ 처음 보는 공고
        │
        ▼
③ 위치 찾기 ── 사업 유형, 공고일, 접수기간, 기준일, 소득표 쪽, 계층 키워드 쪽  (notice_intake 재사용)
        │
        ▼
④ 사업 템플릿 선택 ── 같은 사업의 생성 스크립트 = 규칙 골격 + 빈칸 목록(파라미터 시트)
        │                     └ 템플릿 없음(새 사업) → ⑦ 대신 "아직 판정할 수 없음" + ③의 후보 정보 표시
        ▼
⑤ 빈칸 채우기 ── (a) 결정론 추출기 → (b) 남은 빈칸만 LLM 슬롯 [없음 | Ollama | Claude API]
        │          값마다 {값, 근거 문장, 쪽}
        ▼
⑥ 검증 관문 ── 인용 존재·숫자 일치·기준표 대조·날짜 규칙·범위 점검  → 실패한 빈칸은 '보류'
        │
        ▼
⑥' 규칙 생성 ── 템플릿에 값을 끼워 규칙 JSON (검수 상태 AUTO_DRAFT), 기존 로더의 스키마 검증 통과 필수
        │
        ▼
⑦ 판정 ── 기존 Rule Engine (변경 없음). AUTO_DRAFT 규칙이면 결과에 "검증 전 초안" 표시, 보류 빈칸이 걸린 조건은 '수동 확인'
        │
        ▼
⑧ 운영자 검수 ── 승인하면 정식 등록(원문 대조·골든·테스트·등록 누락 점검) → 이후 업로드는 ②에서 정식 판정
```

## 4. 단계별 설계

| 단계 | 입력 | 처리 | 출력 | 실패하면 | 재사용 자산 |
|---|---|---|---|---|---|
| ① 텍스트 추출 | PDF | 쪽별 텍스트 추출·정규화 | 쪽 텍스트 목록 | 추출 실패 쪽 기록, 그 쪽 근거는 검증 실패 처리 | `source_verify.extract_pages`(캐시 포함) |
| ② 공고 식별 | PDF, 텍스트 | sha256 일치 → 주택관리번호 → 제목+공고일 순 | 등록 공고 ID / 캐시 ID / 없음 | 없음으로 처리 | `notice_intake.registered_as` |
| ③ 위치 찾기 | 쪽 텍스트 | 사업 유형·공고일·접수기간·기준일·소득표 쪽·키워드 쪽 | 후보 보고서 | 후보가 비면 그 빈칸은 ⑤에서 LLM 몫 | `notice_intake.report` (등록 26건 재현율 100%) |
| ④ 템플릿 선택 | 사업 유형 | 같은 사업의 생성 스크립트 템플릿 | 규칙 골격 + 파라미터 시트(빈칸 목록) | 새 사업 → 판정 불가 안내 | `tools/gen_*.py` → 템플릿화 필요 |
| ⑤ 빈칸 채우기 | 빈칸 목록, ③이 찾은 쪽 | 결정론 → LLM(옵션) | 빈칸별 {값, 근거 문장, 쪽} | 못 채운 빈칸은 '보류' | 신규 |
| ⑥ 검증 관문 | ⑤ 결과, 원문 | 7절 규칙 | 통과/보류 표시된 시트 | 보류 | `source_verify` 확장 |
| ⑥' 규칙 생성 | 템플릿, 시트 | 값 끼우기 | 규칙 JSON(AUTO_DRAFT) | 스키마 오류 → 판정 불가 안내 | 생성 스크립트, `rule_data` 로더 |
| ⑦ 판정 | 규칙, 사용자 입력 | 기존 엔진 | 5상태 + 근거 | — | `rule_engine`·`matcher` (변경 없음) |
| ⑧ 검수 | AUTO_DRAFT 규칙 | 사람이 원문 확인·수정·승인 | 정식 규칙 | 반려 사유 기록 | 08 등록 절차·`--audit` |

## 5. 핵심 개념: 사업 템플릿과 파라미터 시트

같은 사업은 차수가 바뀌어도 규칙 **구조**가 거의 같고, 바뀌는 것은 **날짜·한도 같은 값 몇 개**다. 지금의 생성 스크립트가 이미 이 형태다.

| 사업 (생성 스크립트) | 공고마다 바뀌는 값(파라미터) | 예 |
|---|---|---|
| LH 청년매입임대 (`gen_c4_lh.youth_rental`) | 연령 출생일 범위, 만 30세 기준일 | 2차 `"1986.06.26. ~ 2007.06.25."`, `"1996.06.26."` |
| LH 신혼·신생아 매입임대Ⅰ·Ⅱ (`gen_c4_lh.newlywed_rental`) | 유형(Ⅰ/Ⅱ), 혼인 7년 기준일·원문, 6세 이하·신생아 기준일·원문 | 2차 `"혼인신고일이 2019.6.25. ~ 2026.6.25"` |
| LH 든든전세 (`gen_c4_lh.jeonse`) | (규칙 값 변경 없음 — 공고일·접수기간만) | |
| LH 행복주택 (`gen_c1_notices` + `gen_c3_layers` + `gen_c5_housing_weak`) | 공급 계층 구성, 기준일, 지역, 주거약자용 여부 등 — **공고마다 계층 구성이 달라 빈칸이 가장 많다** | |
| SH 신혼·미리내집·장기미임대 (`gen_c4_sh`), 장기전세·장기전세2 (`gen_c5_jeonse`) | 기준일 리터럴(공고일−N년의 다음 날), 소득·자산 한도, 우선공급 기준일 | 50차 `minor_date="2007-04-28"` |

공통 빈칸(모든 사업): 공고일, 접수기간, 원문 PDF 지문.

### 파라미터 시트(⑤의 출력) 예시

```json
{
  "notice_sha256": "…",
  "program": "청년매입임대",
  "template": "gen_c4_lh.youth_rental",
  "fields": {
    "announcement_date": {"value": "2026-12-17", "quote": "공고일(2026.12.17.)", "page": 6, "by": "rule", "check": "pass"},
    "birth_range":       {"value": "1987.12.18. ~ 2008.12.17.", "quote": "…1987.12.18. ~ 2008.12.17. …", "page": 2, "by": "rule", "check": "pass"},
    "under30":           {"value": "1997.12.18.", "quote": "…", "page": 2, "by": "llm:ollama/<모델>", "check": "pass"},
    "schedule":          {"value": [{"start": "2026-12-28T10:00", "end": "2026-12-30T16:00"}], "quote": "청약신청12.28(월)10:00~12.30(수)16:00", "page": 5, "by": "rule", "check": "pass"}
  },
  "held": []
}
```
(숫자는 형식 예시이며 실제 공고 값이 아님)

`by`는 누가 채웠는지(rule / llm:모델명), `check`는 검증 관문 결과, `held`는 보류된 빈칸 목록이다.

## 6. 추출기 슬롯 (⑤)

- **(a) 결정론 추출기**: 날짜·기간·기준일 리터럴·공고일·사업 유형은 이미 정규식 추출이 등록 26건에서 100% 재현됐다(`tests/test_e1_intake.py`).
  소득표는 "등록 기준표와 같은 숫자인가"로 대조한다. **표에 있는 한도(가구원수별 금액 등)와 공급 계층 구성은 결정론으로 어렵다** — LLM 몫.
- **(b) LLM 슬롯 계약** — 어떤 모델이든 같은 계약을 지킨다:
  - 입력: 채울 빈칸 목록(이름·설명·형식), ③이 찾은 쪽의 텍스트만(문서 전체 아님), 출력 JSON 스키마
  - 출력: 빈칸별 `{value, quote, page}` — 근거 문장은 **원문 그대로 복사**하라고 지시하고, 찾지 못하면 비워 둔다(추측 금지)
  - 구현 후보: 없음(결정론만) / Ollama(로컬, JSON 스키마 형식 강제) / Claude API(고도화 선택)
- 슬롯은 **판정 엔진에 직접 연결되지 않는다.** 출력은 반드시 ⑥ 검증 관문을 지난다.

## 7. 검증 관문 (⑥)

| 규칙 | 실패 예 | 처리 |
|---|---|---|
| 근거 문장이 그 쪽 원문에 있다(정규화 후 부분 일치) | 모델이 문장을 지어냄·다른 쪽 표시 | 보류 |
| 근거 문장 안에 추출 값(숫자·날짜)이 있다 | 문장은 맞는데 값을 잘못 옮김 | 보류 |
| 소득 금액이 등록 기준표의 같은 가구원수·비율 값과 같다(같은 기준 연도일 때) | 자릿수 오류, 다른 칸 값 | 보류 |
| 날짜 규칙: 기준일이 공고일−N년(LH 당일 / SH 다음 날) 관행과 맞거나 원문 리터럴 그대로 | 연도 오기 | 보류 |
| 범위 점검: 비율 50~250%, 연령 0~120, 접수 시작 > 공고일 등 | 터무니없는 값 | 보류 |
| 템플릿 필수 빈칸이 모두 채워짐 | 필수 빈칸 누락 | 그 빈칸이 걸린 조건 보류 |
| 생성된 규칙이 기존 로더의 스키마 검증 통과 | 구조 오류 | 판정 불가 안내 |

판정 반영: 보류된 빈칸이 걸린 조건은 엔진에서 **수동 확인(MANUAL_REVIEW, 사유 AUTO_EXTRACT_UNVERIFIED — 신설)**이 된다.
따라서 불충족이 없으면 결과는 '보류'이고, 보류 빈칸 때문에 틀린 '신청 가능'이 나오지 않는다.

## 8. 결과 표시와 검수 상태

- 검수 상태에 **AUTO_DRAFT**(자동 추출, 사람 검수 전)를 추가: AUTO_DRAFT → DRAFT(사람이 만든 규칙, 독립 검토 전) → REVIEWED → PUBLISHED
- AUTO_DRAFT 규칙의 판정 결과에는 항상 **"검증 전 초안 — 자동으로 읽은 공고입니다. 신청 전 원문을 확인하세요"**와
  근거 쪽·문장을 함께 보인다. '신청 가능'이어도 같은 표시.
- 화면 상태: 지원 가능 / 지원 불가 / 보류(추가 정보 필요 · 수동 확인 · 자동 추출 확인 필요)

## 9. 평가 방법 (P1)

- **정답지**: 등록 26건의 검증된 규칙(값·근거·쪽). 등록 공고가 늘수록 정답지도 늘어난다.
- **하나 빼고 맞혀 보기**: 같은 사업의 한 공고를 "처음 보는 공고"로 두고 나머지로 만든 템플릿에 ⑤를 돌려 정답과 비교.
- **지표**

| 지표 | 정의 | 의미 |
|---|---|---|
| 빈칸 일치율 | 정답과 같은 값 / 전체 빈칸 | 추출 정확도 |
| 보류율 | 검증 관문에서 보류된 빈칸 / 전체 | 사용자가 보게 될 '보류'의 양 |
| **틀린 통과율** (최우선) | 검증 관문을 통과했는데 정답과 다른 빈칸 / 전체 | 틀린 판정으로 이어지는 유일한 경로 |
| 판정 일치율 | 골든 입력으로 자동 규칙 판정 = 정식 규칙 판정 | 사용자 체감 정확도 |
| 처리 시간 | 공고 1건 ⑤ 소요 | 운영 가능성 |

- **합격 기준(제안, 결정 필요)**: 틀린 통과율 0%, 빈칸 일치율 90% 이상, 판정 일치율 95% 이상이면 P2(사용자 업로드 초안 판정) 진행.

## 11. 추출 엔진 내재화 전략

"우리가 모은 공고로 우리만의 추출 엔진을 만들 수 있는가"에 대한 설계 답:

| 선택지 | 가능성 | 판단 |
|---|---|---|
| 모델을 처음부터 학습 | 데이터(26건)·연산 모두 턱없이 부족 | ✗ (설계 문서 v0.1도 "자체 LLM 학습"을 MVP 제외로 둠) |
| 작은 공개 모델 미세조정(LoRA) | 학습 예시는 만들 수 있음(조건마다 값+근거+쪽이 있어 수백 개의 라벨) — 하지만 26건이 같은 템플릿 몇 개에 몰려 있어 **새 표현에 일반화가 약하고**, VRAM 4GB에선 학습도 빠듯 | △ 등록 공고 100건 이상 쌓인 뒤 재검토 |
| **엔진 내재화(추천)**: 사업 템플릿 + 결정론 추출기 + 검증 관문 + 정답 데이터셋을 우리가 소유, LLM은 교체 가능한 슬롯 | 지금 자산 대부분이 이미 있음 | ✅ |

내재화의 실체는 모델 가중치가 아니라 **공고 구조에 대한 지식**(어떤 사업이 어떤 빈칸을 갖는지, 원문에서 어디를 봐야 하는지, 무엇이 맞는 값인지
확인하는 규칙)과 **정답지**다. 이 둘이 있으면 모델은 Ollama든 Claude API든 나중의 미세조정 모델이든 같은 정답지로 평가해 갈아끼우면 된다.
등록 공고 하나하나가 자동으로 정답지와 (미래의) 학습 데이터가 된다.

P2(합격 5개 사업의 미등록 공고를 '검증 전 초안'으로 판정)는 기술적으로 가능하지만, 열기 전에 다음을 막아야 한다.

1. **기준표 연도 확인(필수)** — 기준표를 직접 참조하면서 인용문에 금액이 없는 조건은 연도가 바뀌어도 인용문이 그대로 찾아진다.
   예: 청년매입임대 3순위 본인 소득(`T3-income`, "전년도 도시근로자 1인 가구 …") — 다음 해 공고에서 **옛 기준표 금액으로 판정**될 수 있다.
   → 검증 관문에 "템플릿이 쓰는 기준표의 대표 금액이 새 공고 원문에 있는지" 점검을 추가, 없으면 소득 조건(또는 공고 전체) 보류.
2. **템플릿에 없는 새 조건** — 인용문 대조는 '있는 조건이 맞는지'만 보고 '없는 조건이 새로 생겼는지'는 못 본다(예: 지역 제한 추가).
   → 알려진 제한 문구(“이번 공고에서는 모집하지 않음”, “○○ 거주자만” 등) 점검, 결과에 "검증 전 초안" 표시.
3. **근거가 얇다** — 합격 5개 사업은 시험용 공고가 각 1건뿐이고, 템플릿은 등록 26건에서 나왔다. → 사용자가 넣을 실제 새 공고로
   두 번째 시험을 거친 뒤 공개하거나, 먼저 운영자 미리보기로만 연다.
4. **표시·책임** — 초안 판정은 등록(검증) 판정과 화면에서 분명히 구분(배지·문구·근거 쪽), 보류가 많을 수 있음을 안내.
5. **코드 위치** — 템플릿·추출기가 tools/에 있다. 앱에서 쓰려면 src/로 옮기거나 앱이 tools/를 불러오게 정리.
6. **범위가 좁다** — 가장 흔한 행복주택은 아직 조건부(1순위 지역 조건)라 초안 판정 대상에서 빠진다.

## 19. 표 칸 위치 읽기 — T1·T2·T5 평가 (2026-11-01, 판정 경로 미연결)

**배경(OCR 검토, 2026-11-01)**: 샘플 공고 48건 1,908쪽에서 스캔 PDF 0건, 글자 없는 쪽 33쪽은 표지·MEMO·홍보 그림뿐 — 자격 조건은
전부 pypdf로 읽힌다. 문제는 OCR이 아니라 **표 구조**: pypdf는 표를 한 줄로 풀어 빈 칸(병합 셀)이 사라진다("80% 4,693,016원 …"의
첫 값이 몇 인 가구인지 모름). 그래서 지금은 표 값을 "그 숫자가 쪽 어딘가에 있나"로만 확인한다. 유료 OCR(Mistral OCR) 보조는
효과 대비 비용이 불확실해 **보류**(사용자 결정), PaddleOCR-VL은 중국 개발 모델이라 제외. 로컬 소형 모델에 표 이미지를 읽히면
(ministral-3:3b) 113초·값 누락 3·오독 2 — OCR 대용 불가.

**구현(평가 범위 — 사용자 결정 (a)안: T1·T2·T5만, 적용은 결과를 보고 결정)**
- `src/pdf_tables.py`(pdfplumber 0.11.9 — 0.11.10은 Pillow ≥12.2를 요구해 streamlit과 충돌): 표 후보 쪽(`income_pages` 등)만 두 방법으로 읽는다.
  `lines` = 표의 선으로 칸 나누기, `words` = 같은 영역의 글자 좌표로 줄을 묶고 금액 글자의 가로 위치로 열 맞추기(세로선 없는 표).
- 소득 기준표 해석 `income_cells`: 머리글의 가구원수·비율로 칸마다 (가구원수, 실제 비율, 금액). 처리하는 표 모양 —
  가구원수가 열/비율이 열(전치), 여러 줄 머리글('2인가구' / '(+10p%)'), 1·2인 가산 머리글('+20%p'), **표시 없는 1·2인 가산**(LH 신혼·신생아:
  머리글 70%인데 1인 칸은 90% 금액 — 같은 가구원수의 두 칸 이상으로 0·10·20%p 중 하나로 풀고, 못 풀면 버림), 구간 머리글('~30%'),
  '100퍼센트' 표기, 머리글 괄호 속 가구원수별 비율('월평균소득50%(1인가구70%,2인가구60%)'), 한 줄 표('1인 | 4,576,036원 이하 | 120%').

  ③ 방법 일치 — 두 방법이 같은 칸에 다른 금액이면 그 칸 버림 ④ 기준표 대조 — 등록 기준표를 **기준(도시근로자/기준중위소득)·연도 묶음**의
