# 06. 규칙의 데이터화 설계안 (B단계) — 초안

> 상태: **P1~P3 구현 완료(2026-10-01)** — 3개 공고 전 계층 이전, legacy 삭제, 골든 스냅샷으로 대체.
> 남은 단계: P4(원문 대조 도구·검수 상태 배지). §9의 5개 결정은 모두 권장안대로 확정됨
> (JSON, 원문 대조 검사 포함, 현재 규칙 DRAFT, 필드 레지스트리·우선공급 배점은 제외). 구현 중 설계에서
> 바뀐 점은 §12에 기록.
> 배경: 설계개발문서 v0.1 §5.2 — "기준값은 코드가 아니라 테이블로, 규칙은 버전·출처·검수 상태와
> 함께 관리, 검수된 규칙만 운영 사용". 지금은 규칙·기준값이 전부 `src/notices_data.py`의
> 파이썬 람다와 if-체인에 박혀 있다.

## 1. 왜 지금 하는가
- 공고를 3건에서 20건으로 늘릴 때(C) 지금 방식은 공고당 수백 줄의 파이썬을 새로 짜야 하고, 규칙
  리뷰어는 코드를 읽어야 한다. 규칙을 "원문 표와 나란히 비교 가능한 데이터"로 바꿔야 확장과 검수가
  가능하다.
- 이후 단계(E: AI 파서, 관리자 검수)의 산출물과 입력이 곧 이 데이터다. 구조를 먼저 고정하지 않으면
  AI 파서는 만들 대상이 없다.
- 03번 문서의 한계("기준값이 원문과 다르게 옮겨졌다면 경계 테스트도 통과한다")를 **자동으로 막는
  원문 대조 검사**(§7)를 넣을 수 있다.

## 2. 무엇을 데이터로 옮기고, 무엇을 코드에 남기는가
| 데이터로 이동 | 코드에 남김 |
|---|---|
| 공고 메타(공고일, 출처 문서, 버전, 검수 상태) | 3상태+Review 평가기(우선순위: 불충족 > 해석미확정 > 정보부족 > 충족) |
| 계층별 조건 목록, 조건 ID, 필수 여부, 안내 문구(`note`) | 닫힌 연산자 집합(§4)과 그 구현 |
| 원문 근거(페이지·항목·인용문) | 허용 목록(whitelist) 함수: `bonus_child_count`, `years_before` 등 |
| 기준값 표(도시근로자 소득표, 자산·자동차 한도 표) | `validate_profile` 같은 입력 검증(→ §8 2단계에서 필드 레지스트리로 이전 검토) |
| 자녀가산 결합표 등 "가구원수×자녀수×맞벌이" 결정표 | `HouseholdProfile` 데이터 모델 |
| 컷오프 날짜(리터럴 또는 공식 이름) | |
| 해석이 갈리는 지점(readings)과 사유 코드 | |

원칙: **규칙이 새 연산자를 필요로 하면 코드 변경+테스트가 필요하다.** 데이터만으로 임의 로직을 쓸 수
없게 해서 데이터 파일이 "프로그래밍 언어"로 번지는 것을 막는다(임의 코드 실행 `eval` 없음).

## 4. 조건 표현 — 닫힌 연산자 집합
값 영역은 4가지다: **충족(T) / 불충족(F) / 정보부족(U) / 해석미확정(R)**. 변수가 `None`이면 비교는
U를 낸다(지금의 `None` 규칙과 동일).

| 종류 | 연산자 | 비고 |
|---|---|---|
| 비교 | `eq` `ne` `in` `lte` `gte` `between` | 한쪽이 None이면 U |
| 결합 | `all` `any` | `any`: T > R > U > F, `all`: F > R > U > T (지금 `evaluate`의 우선순위와 동일) |
| 변수/상수 | `var` `const` `ctx`(공고 컨텍스트: 공고일 등) | |
| 조회 | `lookup`(기준값 표), `table`(결정표, §5) | 표에 해당 행이 없으면 규칙 선언에 따라 U 또는 R |
| 파생값 | `fn`(허용 목록 함수 호출) | 예: `bonus_child_count(children_birth_dates, announcement)` |
| 날짜 | `on_or_after`, `within_years_of`(컷오프 비교) | 지금의 `is_within_years` 방식(정확한 컷오프 비교) 유지 |
| 적용 조건 | 조건별 `when` | 예: "예비신혼부부는 혼인기간 요건 없음" → `when: marital_status == 혼인중` |
| 이행 시점 | 조건별 `timing: NOW \| BEFORE_MOVE_IN` | 청약통장처럼 "입주 전까지" 조건을 현재 충족 조건과 분리해 표시 |
| 자기신고 | 리프에 `review_if_true: {code, detail}` | 사회초년생 경로: T 대신 R |

### 예시 (설명용, 문법은 구현 단계에서 확정)
N3 청년 연령 요건 — 지금의 `_youth_age_or_rookie_ok`:
```json
{
  "id": "N3-R5b", "required": true,
  "label": "19세 이상 39세 이하이거나 사회초년생인지",
  "source": {"page": 7, "clause": "①-㉮/㉯", "quote": "19세 이상 39세 이하인 자"},
  "check": {"any": [
    {"between": [{"var": "age"}, 19, 39]},
    {"eq": [{"var": "is_social_rookie"}, true],
     "review_if_true": {"code": "SELF_REPORT_UNVERIFIED",
                        "detail": "사회초년생 세부요건은 자기신고이며 증빙을 검증하지 않음"}}
  ]}
}
```
`any`의 우선순위 덕분에 나이가 범위 안이면 T, 범위 밖+자기신고 "예"면 R, "아니오"면 F, 모름이면 U —
지금 코드의 분기 4개가 그대로 나온다.

## 5. 결정표(decision table) — 원문 표를 1:1로 옮긴다
자녀가산 결합표처럼 "가구원수×자녀수(×맞벌이)→소득비율·자산·자동차" 구조는 if-체인 대신 **행 목록**으로
쓴다. 리뷰어가 PDF 표와 나란히 놓고 행 단위로 비교할 수 있다.
```json
"tables": {
  "N2_student_terms": {
    "columns": ["household_size", "child_count"],
    "outputs": ["ratio", "asset_limit"],
    "readings": ["AS_WRITTEN", "GENERAL_BONUS_RULE"],
    "rows": [
      {"size": 1,        "child": 0,      "out": [120, 108000000]},
      {"size": 2,        "child": "any",  "out": [110, 108000000], "readings": ["AS_WRITTEN"]},
      {"size": 2,        "child": 1,      "out": [120, 119000000], "readings": ["GENERAL_BONUS_RULE"]},
      {"size": 2,        "child": "2+",   "out": [130, 130000000], "readings": ["GENERAL_BONUS_RULE"]},
      {"size": "3+",     "child": 0,      "out": [100, 108000000]},
      {"size": "3+",     "child": 1,      "out": [110, 119000000]},
      {"size": "3+",     "child": "2+",   "out": [120, 130000000]}
    ],
    "no_row": {"size": 1, "child": "1+", "result": "REVIEW", "code": "AMBIGUOUS_SOURCE"}
  }
}
```
**readings(해석 후보)가 지금의 `resolve_interpretations`를 일반화한다.** 표가 reading을 둘 이상
선언하면 엔진이 reading마다 조건을 계산해 모두 같을 때만 확정하고 갈리면 R로 올린다. 지금 코드의
세 군데가 이 한 장치로 표현된다:
1. 대학생·청년 2인 가구+출생자녀 (위 예시)
2. 청년 세대원+출생자녀의 소득 기준 가구원수 (reading이 `income_household_size` 변수를 1로 바인딩)
3. (향후) 다른 공고에서 같은 종류의 모호성이 나와도 코드 수정 없이 데이터로 선언

## 6. 검수 상태와 버전 (설계문서 §9 연결)
```json
"review": {"status": "DRAFT", "log": []},
"version": 1, "valid_from": "2026-08-19", "supersedes": null,
"source": {"document": "서울번동3_행복주택_예비입주자_표준모집공고문.pdf", "sha256": "…", "pages": 29}
```
- 상태: `DRAFT → REVIEWED → PUBLISHED → RETIRED`. **현재 3개 공고는 모두 `DRAFT`로 시작한다.**
  구조화한 사람과 판정 코드를 만든 사람이 같아서 독립 검토가 없었기 때문이다(03번 문서의 한계).
  독립 검증 워크시트 결과가 일치하면 `REVIEWED`로 올린다 — A단계 작업이 이 상태 전이와 연결된다.
- 화면: 결과에 공고의 검수 상태 배지를 표시하고, `DRAFT` 규칙의 결과임을 숨기지 않는다.
- 운영 정책(후속): 공개 서비스에서는 `PUBLISHED`만 로드.

## 7. 원문 대조 검사 (`tools/verify_sources.py`)
- 모든 조건의 `source.quote`가 해당 페이지 텍스트에 실제로 있는지 검사(오탈자·옮겨 적기 오류).
- 모든 수치 상수가 인용 근거 페이지에 있는지 검사. 표기 변형(`25,100만원`, `251,000,000원`,
  `25,100만`)을 정규화해 찾는다.
- **타당성 사전 확인(2026-10-01)**: 현재 코드의 금액 상수 38개를 3개 PDF 텍스트와 대조한 결과
  38개 전부 원문에 존재했다(공고·페이지까지 특정하지 않은 "어딘가에 존재" 수준). 즉 표기 정규화로
  자동 검사가 가능하고, 현재 값에 단순 옮겨 적기 오류는 없다.
- 한계: 숫자가 *있다*는 것만 보장한다. 숫자를 *어느 조건에 쓰는지*(해석)는 보장하지 못한다 — 그건 여전히
  독립 검증과 LH 확인의 몫이다. 이 검사는 해석이 아니라 전사(transcription) 오류를 막는다.
- CI가 없으므로 당분간 `pytest`에 포함시켜 매 테스트 실행 때 함께 돈다.

## 8. 전환 계획 — 안전망 두 겹
**안전망 1: 기존 172개 테스트를 그대로 통과** — `evaluate()`, `HouseholdProfile`, `explain()`의 공개
인터페이스를 바꾸지 않는다. 화면·설명 계층은 수정 없이 동작해야 한다.
**안전망 2: 차분 테스트(differential test)** — 전환하는 동안 기존 파이썬 규칙(`notices_data.py`)을
`legacy`로 남겨두고, 같은 입력에 새 엔진이 **verdict·matched·failed·unknown·review까지 전부 동일**한지
대량 비교한다. 입력 생성: 데이터의 모든 수치 한도 L에 대해 L-1/L/L+1, 모든 컷오프 날짜의 전날/당일/다음날,
각 enum 값, None/0 조합. 차이 0건이 되면 `legacy` 삭제.

| 단계 | 내용 | 종료 조건 |
|---|---|---|
| P1 | 스키마·로더·평가기(비교/결합/조회/적용조건/이행시점) + `reference/` 이전 + **N2(조건 6개)** 이전 | N2 차분 테스트 0건, 기존 테스트 통과 |
| P2 | 결정표·readings·파생 함수 + **N3 대학생·청년** 이전 | N3 대학생·청년 차분 0건 |
| P3 | **N1, N3 신혼부부·한부모** 이전, `legacy` 삭제 | 전체 차분 0건 → legacy 제거 |
| P4 | `verify_sources.py` + 검수 상태 배지 | 38개 상수 + 모든 인용문 검사 통과 |
| P5 (선택) | 필드 레지스트리: `HouseholdProfile`·`validate_profile`·UI 입력 위젯의 중복 제거 | 별도 합의 후 |
| 검증 | "코드 변경 없이 새 공고가 추가되는가"를 시험하는 **가짜 4번째 공고**를 테스트에 추가 | 파이썬 수정 0줄로 판정 |

## 9. 확정이 필요한 결정 (권장안 포함)
1. **형식: JSON vs YAML** — 권장 **JSON**. 설계문서의 AI 파서(JSON Schema 출력)·PostgreSQL JSONB와 직결되고
   표준 라이브러리만으로 읽혀 의존성이 늘지 않는다. 단점은 주석이 없는 것인데, 사람이 읽을 설명은
   `note`/`source.quote` 필드로 담는다.
2. **원문 대조 검사(§7)를 B에 포함** — 권장 **포함**. 비용이 작고 03번 문서의 한계를 직접 줄인다.
3. **현재 규칙의 검수 상태** — 권장 **전부 `DRAFT`**. 독립 검토가 없었으므로 솔직한 표기가 안전하다.
4. **필드 레지스트리(P5)** — 권장 **B 1차에서는 제외**. 효과는 크지만 UI 재작성이 따라오므로 규칙 이전이
   끝난 뒤 별도 결정.
5. **우선공급 배점(`priority_scoring.py`)** — 권장 **B 1차에서는 제외**(verdict와 분리된 별도 점수).
   같은 방식으로 후속 이전.

## 10. 위험과 대응
| 위험 | 대응 |
|---|---|
| 연산자가 늘어나 데이터가 프로그래밍 언어가 됨 | 닫힌 집합. 새 연산자는 코드+테스트 변경으로만 추가 |
| 차분 테스트가 놓치는 입력 | 한도·컷오프에서 자동 파생하는 경계 입력 + 기존 172개 테스트를 이중 안전망으로 유지 |
| 데이터 오류가 런타임에서야 드러남 | JSON Schema 검증 + 로드 시 참조 무결성(존재하지 않는 표·필드 참조) 검사 |
| 규칙을 읽기 어려워 리뷰가 안 됨 | 결정표를 PDF 표와 같은 행 구조로 유지, 조건마다 `quote`와 쪽수 필수 |
| 전환 중 두 벌 유지로 불일치 | `legacy`는 읽기 전용 기준선으로만 두고 P3에서 삭제 |

## 11. 하지 않는 것
DB 저장, 관리자 화면, AI 파서, 자동수집, API(프로필 저장 포함) — 이 구조가 먼저 고정돼야 의미가 있다.

## 12. P1 구현 결과와 설계 변경점 (2026-10-01)
구현: `src/rule_data.py`(로더·조건식 컴파일러), `rules/reference/income_standard.json`,
`rules/notices/N2.json`, `tests/test_rule_data.py`. 기존 `evaluate()`/`explain()`/화면은 수정하지 않았다
(로더가 기존과 같은 `RuleCondition`/`NoticeRuleSet` 객체를 만든다).

설계에서 달라진 점:
1. **P1의 범위가 커졌다.** N2의 소득·자산 조건이 이미 결정표+readings를 쓰므로 P2로 미뤘던 결정표와
   readings, 파생 함수를 P1에서 같이 구현했다. 대신 P2는 청년의 "reading이 변수를 바인딩하는" 경우
   (세대원 소득 가구원수 1 고정)와 신혼부부·한부모 표, `when`, `timing`에 집중한다.
2. **JSON Schema 파일은 만들지 않았다.** 쓰지 않는 스키마 파일은 오해만 부른다. 대신 로더가 로드 시점에
   구조·참조를 검증한다(알 수 없는 연산자/변수/함수/표/컨텍스트, ID 중복, 행 표기, 검수 상태 등 19가지를
   테스트로 확인). JSON Schema는 AI 파서(E) 단계에서 출력 형식으로 필요해질 때 만든다.
3. **날짜 비교는 `gte`/`lte`로 쓴다.** `on_or_after` 연산자는 불필요해서 뺐다. 컷오프는
   `{"fn":"years_before"}`로 계산한다.
4. **연산자 보조 키를 명시했다.** `fn`은 `args`, `var`는 `unknown_values`(예: 자동차가액 "확인불가"를
   None으로)만 함께 쓸 수 있고, 그 외 키(철자 오류 포함)는 로드 시 거부한다.
5. **None > 표에 없음 > 해석 불일치** 순서로 전파한다(기존 코드의 "소득이 None이면 표 조회 전에 정보 부족"
   순서를 그대로 재현).

검증 결과:
- 차분 테스트: 기존 N2와 데이터 N2가 verdict·score·matched·failed·unknown·review(사유 코드와 상세 문구)까지
  동일. 무작위 4만 건(통과 영역에 가중) + 결정표·소득·자산·재학/졸업 경계 전수 조합.
  표본 분포: ELIGIBLE 13% / MANUAL_REVIEW 7% / NEEDS_INFO 4% / INELIGIBLE 76%.
- **하네스 민감도(변이 테스트)**: 데이터를 일부러 틀리게 바꾼 6가지(자산 한도 1M 차이, 비율 120→110,
  reading 행 삭제, 졸업 2년→3년, 자동차 0→1, 재학 목록 항목 삭제)를 모두 잡아냈다. 처음에는 표본이
  ELIGIBLE 1%뿐이라 통과 영역이 거의 검증되지 않아 표본을 가중하도록 고쳤다.
- 인용문 검증: N2의 `source.quote` 7개가 지정한 쪽 PDF 텍스트에 모두 존재(공백 정규화). P4에서 도구화.
- 공고 PDF의 sha256을 데이터에 기록하고 테스트로 대조한다(원문 파일이 바뀌면 실패).

## 16. P4 결과 (2026-10-07): 원문 근거 자동 대조 + 검수 상태 배지
