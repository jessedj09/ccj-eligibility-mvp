# 03. 검증 방법론 — "36/36 통과"가 의미하는 것과 의미하지 않는 것

## 프로필(P01~P12)은 실제 신청자 데이터가 아니다

전부 합성 데이터다. `reference_values`의 정확한 기준선(예: 3인가구 100% =
8,168,429원)을 알고, **그 기준선에서 의도적으로 위/아래로 배치**해서 특정 로직
분기를 직접 찔러보려고 만든 값이다. 예:

- P01/P02: 기준선에서 확실히 멀리(여유있게 통과 / 확실히 탈락)
- P07: 일반 110%는 초과하지만 맞벌이 130%는 미만인, **분기 로직 정중앙**에 정확히
  배치한 값
- P11/P12: 같은 세대(자산 동일)인데 세대주/세대원 신분만 다르게 설계한 짝 비교

## 검증 절차 (실제로 한 순서)

1. **정답지를 코드보다 먼저 만든다.** 워크북 `match_matrix` 시트에서 사람이(=Claude가
   사용자와 함께) 손으로 각 프로필의 숫자를 `reference_values`에 대조해 verdict를
   미리 계산 → `src/profiles_data.py`의 `EXPECTED` 딕셔너리.
2. 같은 숫자를 코드(`HouseholdProfile`)로 그대로 옮긴다 — 다시 만들지 않고 복사.
3. 12개 프로필 × 3개 공고 = 36개 조합을 `evaluate()`로 전부 돌린다.
4. 결과와 `EXPECTED`를 문자열 비교로 자동 대조한다 (`tests/test_regression.py`).

## 이 검증이 잡아낸 것 (실제 사례)

P12(청년 세대원)를 코드로 옮기는 과정에서, "세대원이면 비율만 120%로 맞추면
된다"고 짰다가 `income_threshold()` 호출 시 실제 가구원수를 그대로 넘겨버리는
버그를 발견 → 수정. (`docs/01-decisions-log.md` 5번 항목)

## 이 검증이 **못 잡는 것** — 반드시 이해할 것

이 테스트는 **"내가 손으로 계산한 것"과 "내가 짠 코드"가 서로 다르게 동작하는지**만
확인한다. 정답지도 Claude가 만들었고 코드도 Claude가 만들었다. 그래서:

- 만약 애초에 공고문의 규칙 자체를 잘못 이해했다면, 그 잘못된 이해가 정답지에도
  코드에도 **똑같이** 들어가 있을 것이고, 36/36이 나와도 **틀린 채로 일치**하는
  것이다.
- 이건 "회귀 방지"(regression prevention)에는 매우 효과적이지만, "규칙 이해 자체의
  정확성"에 대해서는 아무것도 보장하지 않는다.

## 독립 검증은 아직 수행되지 않았다

다음 중 하나가 이루어져야 진짜 독립 검증이라고 부를 수 있다:

1. 실제 사람(도메인 전문가, 예: 사업기획팀 내 LH 청약 경험자)이 몇 개 케이스를
   Claude와 무관하게 직접 계산해서 대조
2. 동일 조건을 LH 공식 자가진단 도구(마이홈포털 등)에 입력해서 결과 대조

이 프로젝트를 이어받는 사람은 위 독립 검증을 언제, 어떻게 수행할지를 우선순위
목록(`docs/04-open-items-and-next-steps.md`)에서 확인하고 계획해야 한다.

## 경계값 테스트(`test_boundaries.py`)에 대한 동일한 한계

경계값 테스트("기준값과 같으면 PASS, +1이면 FAIL")는 **코드의 `<=`/`<` 연산자 구현
오류**를 100% 잡아낸다는 점에서 확실히 가치가 있다. 하지만 기준값 자체
(예: 345,000,000원)가 원문과 다르게 잘못 옮겨졌다면, 그 잘못된 값을 기준으로
경계 테스트를 해도 여전히 통과한다 — 이 역시 "내부 일관성" 검증이지 "원문과의
일치"를 보장하지 않는다.
