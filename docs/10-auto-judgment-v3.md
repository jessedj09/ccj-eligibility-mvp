## 1. 왜 바꾸나 — 지금 구조의 한계(데이터)

2026-10-28 전체 23건 추출 평가(`eval_extraction --set all -v`): 보류 41개 중 대부분이 **값이 아니라 근거 문장** 때문이다.

| 막힌 곳 | 보류 빈칸 | 원인 |

보류로 떨어진다. 또 사업 템플릿이 없으면(그 밖의 모든 사업) 판정할 수 없다.

## 2. 구조 — 세 가지 전환과 안전장치

### 2-1. 조건 부품 사전 (사업 템플릿 → 조건 유형 조립)

새 공고 = 조건 유형의 조립. 사업 템플릿은 "이 사업이면 보통 나오는 조건 목록"(기대 목록)으로만 쓴다.

### 2-2. 값 검증 + 근거 위치 (문장 닮음 검증 폐지)
- **값이 있는 조건**(금액·%·날짜·지역 목록): 값이 원문 문장에 실제로 있는지 대조하고, 교차 확인한다 —
  지명은 시군구 표준 사전(`rules/reference/regions.json`), 기준일은 "공고일 −N년(LH 당일 / SH 다음 날)" 규칙,
  소득 금액은 기준표(`income_standard*.json`), 금액 단위·자릿수.
- **값이 없는 고정 조건**(무주택 세대구성원 등): 신청자격 절에 그 조건의 기준 표현(유형별 앵커)이 있는지.
- 근거 문장 = 그 값(또는 앵커)을 담은 원문 문장 — 형제 공고 문장과 닮을 필요가 없다. 원문 근거 표시는 그대로 유지.

### 2-3. 사용자 단위 확정 (공고 단위 보류 → 후보값 전파)
- 확실하지 않은 값은 **후보 여러 개**로 둔다(예: 지역 목록 후보 A/B). 엔진이 후보마다 판정해 **그 사용자의 결과가 모두 같으면 확정**.
- 갈릴 때만 보류 — "다른 조건은 모두 충족, 이 조건 1개만 원문 p.N에서 확인"처럼 지점을 짚는다.

### 2-4. 조항 장부 (모르는 조건을 적극적으로 찾는 안전장치)
- 신청자격 절의 모든 문장에 꼬리표: ① 어떤 조건 유형의 근거 ② 판정과 무관(서류·일정·순위 내 경쟁·안내) ③ 정체 불명.
- **③이 없어야** "자격 조건을 빠짐없이 읽었다". ③이 남으면 그 문장이 걸린 계층의 등급을 낮춘다.
- 분류는 결정론 규칙 먼저, 남은 문장은 LLM(로컬)이 분류 제안 → 원문 대조 후에만 반영. (지금의 '새 제한 문구' 목록을 대체)

### 2-5. 판정 등급과 운영
| 등급 | 조건 | 사용자에게 |
|---|---|---|
| 검증됨 | 운영자 확인(등록 26건 + 승인된 공고) | 일반 판정 |
| 자동 확정 | 모든 조건 값 검증 + 조항 장부 완결 + 추출 방법 간 일치 | 일반 판정 (표시 문구는 결정 대기 — 7절) |
| 부분 확정 | 일부 값이 후보 | 결과가 안 갈리는 사용자는 확정, 갈리는 사용자만 "조건 1개 확인" |
| 판정 불가 | 사전에 없는 핵심 조건, 스캔 PDF 등 | 후보 정보 + 분석 대기열 |

- 즉시 경로(서버, 수 초): 결정론만. 보강 경로(운영자 PC의 Ollama, 비동기): 남은 후보·미분류 문장 → 등급 상승.
  결과는 원문 지문(sha256)으로 공유 — 같은 공고를 올리는 모든 사용자가 받는다.
- 운영자 검토는 예외만(위험 큰 순). B2 비교를 사업별 정확도 지표로 상시 — 위험 1건이면 그 사업 자동 강등.
- 기능 ②(LH·SH 공고 자동 수집)는 같은 파이프라인의 입구 하나를 더 다는 것.

## 3. 저장 (2026-10-28 결정: DB + git 역할 분담, **PostgreSQL = Neon**)
- **git**: 검증된 규칙의 원본(PR·CI·골든) — 지금 그대로.
- **PostgreSQL(Neon 무료: 프로젝트당 0.5GB·월 100 CU-시간, 5분 미사용 시 절전 → 접속하면 자동으로 깸)**: 공고 목록·등급·
  자동 분석 결과·작업 대기열·분석 중인 공고 PDF. 코드는 일반 PostgreSQL(psycopg)에 맞춰 업체 교체 가능하게.
- 사용자 조건(개인정보)은 저장하지 않는다. 업로드 PDF는 LH·SH 공고로 확인된 것만 보관.
- 운영자 PC 작업기는 바깥으로만 연결(DB 폴링) — PC에 들어오는 접속 없음.

**PDF 보관(별도 파일 저장소 없이)과 위험 대책**
| 위험 | 대책 |
|---|---|
| 용량(0.5GB) 초과 | PDF는 **분석이 끝날 때까지만**(등급 확정·검토 완료) 보관 후 삭제, 지문(sha256)·출처 주소만 남김. 파일당 상한 20MB, 보관 상한(예: 대기 PDF 합계 300MB) 넘으면 새 업로드는 즉시 판정만 하고 보관하지 않음. 실측 평균 1MB/건 |
| 지운 뒤 원문이 다시 필요 | LH·SH 원문은 공고 페이지에서 다시 받을 수 있고, 검증된 공고 원문은 git(sample_lh·sample_sh)에 있다. 업로드 공고는 같은 파일을 다시 올리면 지문으로 이어진다 |
| 절전에서 깨어나는 지연 | 첫 접속 1초 안팎 — 화면은 DB 없이도 즉시 판정(결정론)하므로 판정이 막히지 않는다(DB는 공유 캐시·대기열) |
| DB 장애·접속 실패 | 화면은 DB 없이 동작(그 공고만 매번 새로 분석), 작업기는 재시도. DB는 원본이 아니다(원본 = git·공고 원문) |
| 월 사용량(100 CU-시간) 초과 | 절전 상태는 사용량이 0. 베타 규모에서는 여유 — 사용량을 주 1회 확인 |
| 개인 문서가 잘못 올라옴(주소 공유 베타) | LH·SH 공고로 식별된 PDF만 저장, 나머지는 분석 후 즉시 폐기 |

## 3-1. 결과 표시(2026-10-28 결정)
- **검증됨·자동 확정 모두 배지 없이** 일반 판정으로 보인다. 일부 확인 필요(해당 사용자에게만 "이 조건 1개만 원문 p.N에서 확인")와
  판정 불가(판정 없이 안내)는 2-5절대로.
- 공통 문구(제안): "판정 근거는 조건별로 표시한 공고문 원문입니다. 최종 자격은 공고 기관의 서류 심사로 확정됩니다."
  '참고용 판정' 표현은 쓰지 않는다.

## 3-2. 분양 일반공급(2026-10-28 결정)
- 일반공급 **순위 자격**(1·2순위)까지 판정, 순위 안의 경쟁(순차제 납입 인정금액 순·추첨·가점)은 안내만.
- 청약통장 가입일·납입 횟수·납입 인정금액·해당 지역 거주기간은 **필수 입력**(대부분 판정에 필요). 단 '모름'을 예외로 두고,
  고르면 "정확한 판정이 어려울 수 있습니다" 안내 — 그 조건이 판정에 쓰이면 정보 부족.
- 규제지역(투기과열지구 등)에 따른 1순위 요건은 공고 원문에서 읽는다(새 조건 유형).

## 8. 진행 기록
### ①-1 근거 문장을 값·핵심 표현으로 다시 찾기 (2026-10-28)
`sheet_extract.relocate` — 형제 문장(이 공고 날짜로 맞춤)과 숫자를 가린 글자의 65% 이상이 맞고, 6글자 이상 같은 핵심 표현이
있고, **형제 문장의 값(금액·비율·나이·기간)·날짜·Ⅰ/Ⅱ 유형이 모두 같은** 원문 구간을 근거로 쓴다. 형제마다 찾아 가장 잘 맞는 곳,
내용이 다른 곳이 비슷하게 맞으면 보류. 순서: 그대로 → 숫자만 다름 → **값·핵심 표현(신규)** → LLM.

평가도 엄격하게: 근거 문장이 정답 시트와 **같은 곳**인지 본다(`same_place`) — 다른 곳이지만 값이 어긋나지 않으면
'다른 곳·같은 값'(ALT), 값이 다르면 틀림. 실제 새 공고 조건 평가 `eval_extraction --loo`(형제 = 같은 사업 등록 공고 전부, 자기 제외).

| 평가(23건, 결정론만) | 보류 | 틀림 | 다른 곳·같은 값 | 자동 채움 |
|---|---|---|---|---|
| --loo, 개선 전 | 22 | 0(+같은 값 1) | — | 90% |
| **--loo, 개선 후** | **11** | **0** | 1 | **95%** |
| 시험용 판정 일치(141,520건) | — | 확정 판정 틀림 0 | — | 같음 76.8% → 77.1% |
