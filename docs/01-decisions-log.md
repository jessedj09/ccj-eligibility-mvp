# 01. 설계 결정 로그 (Decisions Log)

> 이 문서는 시간 순서대로 쌓인 "발견 → 논의 → 결정"의 기록이다. 같은 실수를
> 반복하지 않으려고 남긴다. 새로 합류하는 사람(또는 Claude Code)은 이 문서를
> 코드보다 먼저 읽어야 한다.

## 1. score = 충족 필수조건 수 / 전체 필수조건 수 (당첨확률 예측 아님)

score를 "단순 충족비율"로 할지 "가중치 있는 당첨가능성 점수"로 할지 논의 끝에
전자로 확정했다. 근거: 최초 사업기획 문서(v0.1)의 "MVP에서 제외하는 것" 항목에
**"당첨확률 ML 모델"**이 명시적으로 빠져 있다. score를 당첨 가능성으로 정의하면
이 원칙과 충돌한다.

우선공급·가점 항목(청약통장 납입횟수 등)은 이 score에 절대 합산하지 않는다 —
`priority_score`라는 완전히 별개의 필드로 분리한다. (`src/priority_scoring.py`)

## 2. verdict는 3상태가 아니라 4상태다 — `NOT_OFFERED` 발견 경위

파일럿 공고 3건(N1 공릉/N2 관악봉천/N3 번동3)을 실제로 비교해보니 계층 구성이
전부 달랐다: N1=신혼부부·한부모만, N2=대학생만, N3=전체. 기존
`ELIGIBLE/INELIGIBLE/NEEDS_INFO` 3상태로는 "이 공고에는 이 계층 자체가 없다"와
"조건을 못 맞춰서 떨어졌다"를 구분할 방법이 없었다. 둘을 같은 `INELIGIBLE`로
처리하면 사용자에게 "왜 신혼부부인데 대학생 전용 공고에 안 뜨는지"를 설명할 수
없다. 그래서 `NOT_OFFERED`를 추가했다.

## 3. 청약통장 "입주 전까지" 이행기한 문제

공고문 다수 조건(청년 ⑤, 신혼부부 ⑤)이 "본인 또는 배우자 중 1인이 **입주 전까지**
가입사실을 증명할 수 있을 것"으로 되어 있다. 즉 신청 시점에 미가입이어도 신청
자체는 막지 않는다.

**최종 결정**: verdict는 이 조건 때문에 막지 않는다(신청 시점 미가입 → 그래도
ELIGIBLE 가능). 다만 실제로 "청약저축 납입횟수"가 배점으로 쓰이는 곳
(N1의 우선공급 구간)에서는 미가입 시 배점이 0점이 되어 사실상 경쟁에서 불리하다는
사실을 `priority_score`로 별도 안내한다.

중요한 스코프 제한: 이 배점 문제는 **N1(공릉)의 우선공급 구간에서만 확인됐다.**
N1의 일반공급과 N3(번동3)의 모든 구간은 "순위 → 추첨"(무작위)이라 청약통장 이력
자체가 당락에 영향을 주지 않는다. 이걸 모든 공고에 일반화하면 틀린다.

## 4. 세대주/세대원, 1인가구 여부는 Rule Engine이 추론하지 않는다

청년계층은 세대주면 세대 전체 소득, 세대원이면 본인 소득만 보는데, 처음엔
"신청자가 유리한 쪽을 고를 수 있는 거 아닌가"라는 의문이 있었다. 확인 결과:
**세대주/세대원 여부는 주민등록등본으로 이미 자동 결정된 사실**이고, 신청자는
신청 시점에 본인이 어느 쪽인지 이미 알고 있다. 신청자가 선택하는 게 아니다.

대학생계층의 "1인가구" 여부(원칙은 본인+부모 합산인데, 예외적으로 1인가구
기준이 적용되는 경우)도 같은 원리로 해결했다 — **등본에 본인 혼자만 세대원으로
등재돼 있으면 1인가구**로 본다. Rule Engine이 "왜 1인가구인지"를 추론할 필요가
없다 — 그냥 입력값(사실)이다.

→ 코드 반영: `HouseholdProfile.house_head_status`, `household_size` 필드는
Rule Engine이 계산하는 값이 아니라 프로필 입력값 그 자체다.

## 5. 소득과 자산의 "가구원수" 산정 기준이 서로 다르다 (비대칭 발견)

번동3 공고문의 청년계층 표를 정밀 대조한 결과:
- **소득기준표**: 세대원 행이 "1인가구"만 존재 → 세대원은 소득 판정 시 가구원수를
  무조건 1로 고정.
- **자산기준표**: 세대원도 1인/2인/3인이상 행이 전부 존재 → 자산 판정은 실제
  가구원수를 그대로 사용.

같은 청년(세대원) 신청자라도 소득 계산과 자산 계산에 서로 다른 가구원수를 써야
한다. 이 비대칭을 하나로 합쳐서 구현하면 틀린다. (`src/notices_data.py`의
`_youth_income_ok` 함수 주석 참조 — 이 함수는 소득만 계산하고, 자산은 별도
조건(N3-R8)에서 실제 `household_size`를 그대로 쓴다.)

이 지점에서 실제로 코드 버그를 하나 잡았다: 처음 구현할 때 "세대원이면 비율만
120%로 맞추면 된다"고 짰다가, `income_threshold(household_size, 120)`을 호출하면서
실제 가구원수(예: 3)를 그대로 넘겨 잘못된 기준액(3인가구의 120% 값)을 조회하는
버그가 있었다. 프로필 P12(세대원, household_size=3)로 검증하다가 발견 → 가구원수를
1로 명시적으로 고정하도록 수정. (`tests/test_boundaries.py`의
`test_youth_member_income_fixed_at_1in_*` 테스트가 이 버그의 재발 방지용이다.)

## 6. N3에는 우선배정 배점표가 아예 없다 (N1과 다름)

N1(공릉)은 우선공급(2세미만 자녀) 구간에 명시적 배점표(거주지·거주기간 +
청약저축 납입횟수)가 있다. N3(번동3)를 재확인한 결과, 대학생·청년·신혼부부
전 계층에서 "경쟁 시 선정기준 = 순위 → 추첨"만 명시되어 있고, 우선배정
(2세미만 자녀 30%) 구간도 별도 배점 없이 같은 지역순위+추첨을 쓴다. 즉 이 공고는
**애초에 가점제 자체가 없다** — "찾다가 놓친 것"이 아니라 "원래 없는 것"이다.

## 7. N1 우선공급 배점 ①항목(거주지·거주기간)의 적용범위

원문에서 실제 점수표(노원구 3년이상=3점/미만=1점, 청약저축 24회이상=3점/6~23회=1점)를
찾았지만, 인쇄 위치가 "3-2 주거약자용주택" 섹션이었다. "3-1 일반 우선공급" 섹션에는
"2순위 배점항목은 ②만 적용"이라는 동일 문구만 있고 실제 점수표가 없었다.

**사용자 확인(도메인 지식)으로 최종 정리**: 1순위(노원구 거주자)는 ①②둘 다 배점,
2순위(노원구 외 서울시)는 애초에 노원구 거주자가 아니므로 ①항목 자체가 적용될 수
없어서 ②만 배점된다. 이 해석이 논리적으로 자연스럽지만, **점수표 자체가 일반
우선공급에도 재사용되는지는 정황 증거일 뿐 문서로 100% 확정되지는 않았다** —
실사용 전 LH청약플러스나 고객센터 재확인을 권장한다는 caveat을
`priority_scoring.py`의 리턴값에 항상 포함시킨다(테스트로 강제됨).

## 8. 자녀수 가산 — 소득비율·자산·자동차가 동시에 바뀌는 결합표

처음엔 "자산 한도만 자녀수에 따라 올라간다"고 단순화했었는데, 원문 재확인 결과
**출생자녀 수(2023.3.28 이후 출생 기준)에 따라 소득 인정비율·자산 한도·자동차
한도가 동시에** 바뀐다. 그리고 신혼부부(맞벌이 여부로 갈림)와 한부모가족
(맞벌이 개념 없음, 가구원수 구간도 다름: 2인/3인이상 vs 신혼부부의 2인/3인/4인이상)의
표가 서로 다르다. `src/notices_data.py`의 `spouse_terms_married` /
`spouse_terms_singleparent` 두 함수로 분리 구현했다.

## 9. 검증(테스트)의 근본적 한계 — 반드시 읽을 것

MVP0 단계 검증(36개 케이스 100% 일치, 이후 82개 pytest 전부 통과)은 **"내가 손으로
계산한 정답지"와 "내가 짠 코드"가 서로 다르게 동작하는지**만 잡아낸다. 만약
애초에 공고문 규칙 자체를 잘못 이해했다면, 정답지와 코드 둘 다 똑같이 틀린 채로
"일치"한다 — 이 테스트는 그런 종류의 오류를 못 잡는다. 자세한 건
`docs/03-validation-methodology.md` 참조. **아직 실제 사람(도메인 전문가)이나
LH 공식 자가진단 도구를 통한 독립 검증은 수행하지 못했다.**
