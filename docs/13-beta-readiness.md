1. **공고 단위 확인** — 검증 중 사업의 접수 중·예정 공고를 운영자 대기열에 올리고, 운영자가 자동으로 읽은 값을 원문 위치와 나란히 보고 '확인'.
   확인된 공고는 모든 사용자에게 확정 판정. 이 확인은 B2 비교 1건으로도 쌓여 사업이 '검증됨'으로 빨리 올라간다. 사용자가 올리기 전에 미리 할 수 있다.
   한계: 추출만 확인한다(판정 틀 해석은 워크시트 몫). 형식적 확인을 막으려면 값마다 원문을 대조하는 체크리스트로.
2. **보류를 '좁혀진 확인'으로** — 검증 중 사업의 '지원 가능'은 "자동 판정으로는 모든 조건 충족 — 이 사업은 검증 중이라 아래 n개를 원문에서
   확인하세요(쪽·문장)"로 보인다. 이미 있는 '원문 확인 N건' 표시(`src/grading.py` judge)를 다시 쓴다. 흥신소에서는 '지원 불가'와 섞지 않고 '확인 n건'이 적은 순.
3. **확인 항목 줄이기 — 사업×조건 단위 검증 기록** — 독립 검증 사례가 맞힌 조건을 '검증됨'으로 기록해 확인 목록에서 뺀다. 워크시트를 채울수록 보류가
   바로 준다. 조건 이름이 같아도 사업마다 뜻(범위·기준표)이 달라 다른 사업으로 넘기지 않는다.
4. **'검증됨' 경로 여러 개** — 공고가 1년에 한두 번인 사업(SH 영구임대 등)은 3건을 못 채운다. 예: 독립 검증 불일치 0 AND (처음 보는 공고 N건 위험 0 OR
   운영자 확인 공고 M건). 숫자는 T2-2.
5. **'지원 불가' 쪽(놓침 완화)** — 검증 중 사업의 '지원 불가'는 유지하되 원인 조건과 원문 위치를 보여 "이 조건만 확인하면 됨"으로. 흥신소 목록에서 숨기지 않고 접어 둔다.

결정 전에 잴 것: 공고당 운영자 확인 분량(확인할 값 수·시간), 주당 접수 중 공고 수(검증 중 사업), 각 안에서 결과 중 '지원 가능'이 보류로 바뀌는 비율.

**2026-11-14 사용자: 1·2번 방향은 좋으나 사용자가 상시로 직접 확인하기는 어렵다 → 기준을 정해 두고 규칙·파이프라인으로 돌리는 쪽을 검토.**
→ 위 1번(운영자 공고별 확인)은 아래 파이프라인으로 대체한다.

#### '처음 보는 공고 3건' — 정확한 뜻과 출처

- **뜻**: 자동 추출기·판정 틀을 만들 때 쓰지 않은 실제 공고. 절차(docs/08 2-2): ① 등록 전에 자동 분석 결과(초안)를 얼린다(`notice_intake.py --save-draft`
  → `docs/draft-checks/*.draft.json`) — 이때는 그 공고가 형제 공고에 없어서 자동 분석이 '처음 보는' 상태 ② 정식 등록(규칙 JSON — 원문 대조 도구 통과)
  ③ 같은 가상 신청자(골든 입력 — 계층마다 수백 명)로 얼린 초안 판정과 등록 판정을 화면 표시 기준으로 비교 → '위험'(초안이 확정인데 등록과 다름) 0건.
  이런 공고 3개를 사업마다 채운다는 뜻.
- **'사람 등록'의 실제**: 등록 작업은 Claude 세션이 docs/08 체크리스트와 원문 대조 도구(`verify_sources`)로 하고 사용자가 승인했다. 그래서 자동 추출과
  등록이 같은 해석을 공유할 수 있다(10-31 피드백 11항 — '같이 틀림'은 못 잡는다).
- **출처**: 사용자 결정이 아니라 **PRD v3 13절 '남은 결정'의 제안**("1단계 사업 B2 위험 0 + 새 공고 3건 이상 실측", 10-31 피드백 이전 초안). 저장소에는
  2026-11-01 B단계 커밋(6f864f7, docs/10 334줄 "기준(새 공고 3건 위험 0)")에서 처음 나오고, 같은 날 docs/04 백로그에 "공개 기준(PRD v3 13절)"으로
  적혔다. G4 공공임대(11-01)가 이 기준으로 공개된 유일한 사업이고, 11-02 사용자 결정으로 '권장 절차'가 됐다.
- **근거**: '3'에는 통계적 근거가 없다(한 건은 우연일 수 있으니 여러 건 — 정도의 경험적 숫자). 10-31 피드백 10항이 이미 "초기 점검에는 쓸 수 있지만
  지원 범위 전체의 신뢰성 기준으로는 근거가 더 필요, 사업별·조건 유형별 평가 범위를 관리"하라고 했다.

  표본 검사가 없음(10-31 피드백 12항 "최초 공개 전 검사와 사후 표본 검토를 나누어 설계").

#### 규칙 기반 검증 파이프라인(안) — 사용자 상시 확인 없이

발견: 자동 분석(`src/analysis.py` analyze)은 업로드·수집 때마다 초안 스냅샷을 분석 시각과 함께 DB `analyses`에 이미 저장한다. 즉 **'등록 전에 얼리기'는
이미 자동**이다 — 나중에 등록만 하면 B2 비교를 언제든 할 수 있다.

위험을 둘로 나눠 각각 다른 수단으로 확인한다:
- 판정 틀 위험(사업) → **독립 검증 워크시트** — 사람(사용자)이 사업마다 **한 번**. 상시 작업 아님.
- 추출·새 조건 위험(공고) → **자동 관문 + 사후 표본 비교** — 사람 없이 돈다(등록은 Claude 세션이 묶어서).

| 단 | 언제 | 누가 | 내용 |
|---|---|---|---|
| ① 공고 관문 | 업로드·수집마다 | 자동 | 지금 장치(변형 공고 차단·근거 확인·기준표 연도·표 칸 위치·조항 장부) → 계층 등급(자동 확정/일부 확인). 보강 후보: 조건마다 '형제 공고와 같은 문장·값'인지 '새 값'인지 표시 |
| ② 사업 등급 | 기록이 바뀔 때 | 자동 계산 | 검증됨 / 검증 중 / 멈춤 — 기준(숫자는 T2-2): 독립 검증 사례 불일치 0 AND 처음 보는 공고 비교 위험 0 |
| ③ 사후 표본 비교 | 주기(예: 주 1회) | 수집 자동 + Claude 세션 묶음 등록 | 수집된 공고의 저장된 초안 → 등록 대기열(우선순위: 검증 중 사업 > 영향 사용자 > 마감 임박) → 등록 → B2 자동 비교·기록 → 등급 갱신. 위험이면 기존 자동 멈춤 |

표시 규칙(C안 + 보완):

| 사업 등급 | 계층 등급 자동 확정 | 일부 확인(보류 조건 있음) |
|---|---|---|
| 검증됨 | 지금처럼 확정 | 지금처럼 보류(원문 확인 N건) |
| 검증 중 | '지원 가능' → **좁혀진 확인**(독립 검증이 아직 덮지 않은 조건만, 새 값 먼저) · '지원 불가' → 원인 조건·원문 위치와 함께 유지 | 지금처럼 보류 |
| 멈춤 | 판정하지 않음('정확도 점검 중') | 같음 |

사용자 몫: 워크시트(사업별 한 번 — 베타 전에 채운 사업은 베타 때 '검증됨'이 될 수 있음) + 병합 승인. 보류가 많은 기간은 워크시트를 채우기 전,
즉 **베타 전**에 몰리므로 실제 사용자 영향은 워크시트 범위로 조절된다.

#### A안 + 파이프라인 검토 (2026-11-14 사용자 요청)

A+파이프라인 = 판정 틀이 있으면 결과를 지금처럼 그대로 보이고, 파이프라인(공고 관문·사업 등급·사후 표본 비교·자동 멈춤)은 뒤에서 돈다.

| | A + 파이프라인 | C + 파이프라인 |
|---|---|---|
| 검증 중 사업의 '지원 가능' | 그대로 확정 | 좁혀진 확인 |
| 추출 오류 | 사후 표본 비교로 **발견 뒤** 자동 멈춤 — 비교 주기만큼 틀린 결과가 나갈 수 있음 | 발견 전에도 확인 항목으로 짚음 |
| 판정 틀 해석 오류('같이 틀림') | 워크시트 전까지 못 막음(표본 비교로도 안 잡힘) | 워크시트 전까지 좁혀진 확인으로 막음 |
| 보류 | 늘지 않음 | 검증 중 사업에서 늘어남 |
| 피드백 3절(검증 상태에 따라 공개 범위 구분) | 사용자에게는 구분 없음(내부 관리만) — 표시를 더하면 B+파이프라인 | 답함 |

핵심: 두 안의 차이는 **'베타 때 아직 검증 중인 사업'을 어떻게 보이느냐** 하나다. 베타 범위 사업의 워크시트를 베타 전에 마치면 두 안은 같아진다.
그래서 선택지는 사실상 "베타 때 검증 중 사업 = 그대로(A) / 표시(B) / 좁혀진 확인(C) / 베타 범위에서 빼기(D)". 사업마다 피해 크기도 다르다 —
분양은 부적격 당첨의 불이익이 커서(규정 확인 필요) 임대보다 조심할 이유가 있다(사업 유형별로 A·C를 나누는 혼합안 가능).
→ T2-2 숫자(베타 때 검증 중일 사업 수, '지원 가능'이 바뀌는 비율)를 본 뒤 고른다.

'자동 분석이 확신 못 함' 5,915명의 속:

보류로 만들고, 사용자에게 묻지도 못하는 구조다. 공개 원칙(A/C)은 이 문제를 건드리지 못한다.

### 2-4. 담당 세션에 넘기는 요구사항 (2026-11-14 사용자 승인)

공통: 판정은 결정론 그대로(엔진 5상태 불변), 판정 요청·답은 저장하지 않음, API에 더한 동작은 운영자 미리보기와 같은 판정인지 시험으로 맞춤,
화면은 PC·휴대폰 모두 점검. 이 세션은 완료 기준(아래 '확인')을 독립 평가한다.

**R-① 질문형 확인 — ProjectCCJ_work**
- 대상: `grading.judge`에서 엔진 판정이 '지원 가능'인데 그 계층의 확인할 곳이 **미분류 문장(unclassified)·새 제한 문구(restriction)뿐이고 합쳐 3개 이하**일 때.
  원문 확인 못 한 조건(held)이 섞이면 지금처럼 보류(값의 불확실은 사용자가 풀 수 없음). 3개 기준은 설정값으로.
- 질문: 문장마다 원문 문장 전체와 쪽을 보이고 "이 내용 때문에 신청이 막히나요?" — 답 '막히지 않음' / '막힘(해당됨)' / '모르겠음'.
  문장 id는 공고 원문 sha256 + 쪽 + 문장 정규화 해시(같은 공고의 다른 사용자·③과 공유되는 키).
- 다시 판정: 요청에 답(`clause_answers`)을 실어 보낸다. 모두 '막히지 않음' → **지원 가능(원문 n개 본인 확인)**, 하나라도 '막힘' → 지원 불가(본인 확인 — 원문 p.N),
  '모르겠음'이 있으면 보류 유지. 엔진 결과 자체는 바꾸지 않고 표시만(응답에 `user_confirmed` 목록).
- 범위: 재판소(올린 공고)와 흥신소(목록은 '확인 n건' 표시, 상세에서 질문). 4개 이상이면 보류 + ③ 대기열.
- 확인: 질문·답이 서버 로그·DB에 남지 않음, 답 없이 부른 판정은 지금과 같음(회귀), 운영자 미리보기와 같은 판정, 4분류 집계에서 '본인 확인 포함'을 따로 셀 수 있는 응답 필드.

**R-② 보류 나누기 — ProjectCCJ_work**
- 화면 보류를 원인별로: 입력하면 판정(NEEDS_INFO — 지금의 '보류를 질문으로') / 원문 확인 n건(R-①) / 해석이 갈림(AMBIGUOUS_SOURCE — 해석별 결과를 알 수 있으면
  "A로 보면 지원 가능, B로 보면 지원 불가"와 문의처) / 자기신고(SELF_REPORT_UNVERIFIED — "본인이 해당하면 지원 가능") / 입력 확인(INPUT_INCONSISTENT).
- 엔진 5상태·사유 코드는 그대로, 표시(`display_status`)만 나눈다. 4분류 집계에서는 모두 '확정 아님'.
- 확인: 모든 보류가 위 갈래 중 하나와 '다음에 할 일'을 가진다(갈래 없는 보류 0 — 시험).

**R-③ 공고 단위 해소 — ProjectCCJ_work(저장·대기열) + 파싱 세션(R2)**
- 공고마다 미분류 문장 판정을 저장(문장 id → 판정 '조건 아님' / '새 조건' + 출처 '등록' / 'R2+결정론 동의' + 시각). `grading`은 '조건 아님'으로 판정된 문장을 확인할 곳에서 뺀다.
  개인정보 없음(공고문 문장만).
- 출처 1 — 묶음 등록: 파이프라인 ③ 대기열. 대상 = 자동 분석 등급이 '일부 확인'인 공고. 순서 = 접수 중·예정 > 마감 임박 > 이용량 > 검증 중 사업. 등록하면 그 공고는 등록 공고가 되어
  자동 판정 보류가 사라지고, 얼려 둔 초안(DB analyses)과 B2 비교·기록까지 자동.
- 출처 2 — R2(파싱 세션): LLM 문장 분류. **'조건 아님'으로 빼는 것은 R2가 '조건 아님'이고 결정론 표지가 없을 때만** — 결정론 표지 = 조항 장부 STRONG
  표현, 그리고 기준값 패턴(금액·%·기간·나이·날짜). (a) STRONG만 / (b) STRONG+기준값 두 판을 비교해 놓침 0인 판 중 보류가 더 줄어드는 쪽 채택(11-14 파싱 세션과 합의).
  문장 id = `{sha256[:16]}:{쪽}:{sha1(normalize(문장))[:12]}`(R-①과 같은 키, normalize를 바꾸면 해소 기록 다시 계산).
  R2 중간(파싱 세션 11-14, LLM 전): 끼워 넣은 새 조건 24개 중 결정론 표지가 못 막는 것 a(STRONG) 17 / b(+기준값) 11 / c(+부드러운 표현) 0, 실제 미분류 135개 중
  뺄 후보 a 74 / b 50 / c 27(135개 모두 등록 규칙이 쓰지 않는 문장). c판은 파싱 세션이 쓴 24문장으로 골라 과적합 우려 → **이 세션이 패턴을 보지 않고 독립 시험 문장
