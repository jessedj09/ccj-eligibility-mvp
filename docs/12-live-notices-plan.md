## 설계

1. **수집기**: 1~3시간마다 LH API·청약홈 API·서울시 주택포털을 읽어 `live_notices`(출처·외부 ID·제목·사업 유형·지역·공고일·접수기간·상태·
   공식 링크·first/last_seen, 개인정보 없음)에 쌓는다. Render 무료 서버는 잠들므로 GitHub Actions 예약 작업으로 돌린다. 실패하면 알린다.
2. **판정과 잇기**: 수집한 공고마다 등록 공고와 같은 공고인지(제목·공고일·단지명 — `notice_identify` 재사용), 이미 누가 올려 분석된 공고인지,
   판정 틀이 있는 사업인지(`notice_candidates`·`choose_template` 재사용)를 정한다.
3. **흥신소 '지금 모집 중' 영역**: ① 판정 가능(등록·분석 완료) — 지금처럼 판정 ② 판정 틀은 있으나 분석 전 — "공고문을 올리면 바로 판정" +
   공식 링크(한 사람이 올리면 분석이 저장돼 모두 판정) ③ 판정하지 않는 사업 — 이름·기간·링크.
4. **운영자 보조**: 분석 전 새 공고를 운영자 검토 화면에 띄워, 운영자가 PDF를 직접 내려받아 올리면 모두 판정받게 한다.
5. **나중(선택)**: LH API가 첨부 주소를 공식으로 주면 자동 분석까지. 새 공고 알림은 회원 기능과 묶어 그다음 검토.

## 2단계 재설계 — 흥신소 주 흐름 (2026-11-10 사용자 결정)

> "흥신소에서는 판정 기능 제공도 중요하지만 그에 앞서 사용자가 자신의 기본적인 청약 자격조건을 입력하면 현재 지원 가능한 공고 리스트를 띄워 주는
> 형상을 메인 플로우로" — 처음 설계(위 '설계' 3)는 흥신소 결과 아래에 '지금 모집 중' 영역을 **덧붙이는** 것이었다. 이제는 그 목록이 흥신소의 **첫 화면이자 결과**다.
> 기획: `기획서/PRD_v3.md` v3.7 0-1절·흐름 0·F33~F36.

### 풀어야 할 것

마감 안 된 공고 64건(운영 DB, 같은 공고 묶은 뒤) = 등록 7 · **판정 틀 있음·공고문 분석 전 43** · 판정 안 하는 사업 14 안팎. 지금 흥신소는 등록 공고만 판정하므로
그대로 목록을 만들면 "지원 가능"이 몇 건 안 되고 대부분이 '판정 전'이다. 두 갈래로 푼다.

1. **분석 전 공고를 예비 판정** — 같은 사업의 최근 공고(대표 공고) 규칙으로 판정해 '가능성 있음 / 확인 필요 / 어려움'. 공고문 PDF 없이 지금 할 수 있다.
2. **확정 판정 범위를 넓힘** — 올라온 분석(사용자·운영자 업로드)을 수집 공고와 잇고, 운영자가 분석 대기 공고를 처리한다(공고문은 사람이 내려받음 — robots).

### 판정 경로

```
기본 조건 ─▶ POST /find ─▶ 마감 안 된 live_notices ─ merge_duplicates(같은 공고 묶기)
                              ├ 등록 공고(registered_id)        → 그 등록 규칙으로 판정            → 확정
                              ├ 분석된 업로드와 이어짐(F35)      → 그 분석으로 grading.judge(등급)   → 확정
                              ├ 판정 틀 있음·분석 전             → 대표 공고 규칙으로 판정 → 예비로 바꿈 → 예비
                              └ 판정 안 하는 사업                → 판정 없이 이름·기간·공식 링크
                           ─▶ 공고 카드(계층별 결과 요약) + 추가 질문(정보 부족이 가장 많이 걸린 항목 1~2개) + 기준 시각
```

### 예비 판정 (`src/live_judge.py` — 새 모듈)

- **대표 공고 고르기**: 수집 공고의 판정 틀(`choose_template` 결과 = 템플릿 id, 판(edition)이 있는 사업은 같은 판)과 발행 기관이 같은 **등록 공고 중
  공고일이 가장 가까운 앞선 공고**. 없으면 같은 틀의 가장 최근 등록 공고. 판정 틀은 등록 공고로 만들었으므로 판정 틀이 있으면 대표 공고가 늘 있다.
- **계층 맞추기**: 계층 이름의 기본 부분(`layer.split("(")[0]`, `matcher.scope_for`와 같은 방식)으로 대표 공고의 계층을 찾는다. 대표 공고에 없는 계층은
  판정하지 않는다(카드에 "이 공고의 공급 계층은 공고문 확인").
- **결과 바꾸기**(계층마다):

  | 대표 공고 기준 판정 | 예비 판정 |
  |---|---|
  | 지원 가능(ELIGIBLE) | **가능성 있음** — '지원 가능' 표현 금지 |
  | 수동 확인·정보 부족 | 확인 필요(부족한 항목은 추가 질문으로) |
  | 지원 불가 — 걸린 조건이 모두 **공고마다 같은 유형**(무주택·혼인 상태·혼인 기간·자녀 기준·나이·학생·취업·복지 자격·주택 소유 이력) | **어려움**(걸린 조건 한 줄) |
  | 지원 불가 — 걸린 조건에 **공고마다 다를 수 있는 유형**(거주 지역·청약통장·근무·산업·우선공급 유형) 또는 금액 한도(소득·총자산·자동차)가 있음 | 확인 필요 — 금액 한도는 대표 공고와 수집 공고의 **기준 연도가 같을 때만** '어려움' |

  조건 유형은 조건 부품 사전(설계·개발 문서 §4)의 16개 유형을 쓴다. 유형을 모르는 조건으로 걸리면 확인 필요.
- 공고 카드의 요약은 계층 중 가장 좋은 결과(가능성 있음 > 확인 필요 > 어려움), 근거 표시 "같은 사업 최근 공고 ○○(공고일) 기준 — 이 공고문으로 확정 전".

### 되짚어 보기 — 예비 판정을 보이기 전 검증 (`tools/eval_preview.py`)

  비교해 `preview_health`에 쌓고, 놓침 1건이면 그 틀의 '어려움'을 멈춘다(`program_health`와 같은 방식, 다시 켜는 것은 운영자).

### 수집 공고와 분석 잇기 (F35)

- 판정 틀이 있는 수집 공고마다 Neon `notices`(업로드로 분석된 공고 — 기관·사업·제목·공고일)에서 **같은 기관·같은 공고일·같은 사업 키·제목 비슷 0.7 이상**
  (`registered_match`와 같은 기준을 분석 공고로 넓힘)을 찾아 최신 분석(`analyses`)을 쓴다. 정정공고면 정정 뒤 공고일과 맞는 분석만.
- 잇기는 `/find` 때 계산하고(수집 주기와 무관하게 업로드 즉시 반영), 운영자 화면에도 같은 함수를 쓴다.

### API (판정 API, 개인정보 저장 없음)

| 경로 | 내용 |
|---|---|
| `GET /find/form` | 기본 자격조건 양식(`form_spec.basic_form()` — PRD 8절 표의 항목만, 저장 파일·회원 '내 조건'과 같은 이름) |
| `POST /find` | 입력 `{profile, filters: {regions?, kind?: 임대/분양/둘 다, open_only}}` → `{collected_at, stale, counts, items[], questions[]}`. 항목: 공고 키·기관·사업·제목·지역·공고일·접수기간·상태(접수 중/예정)·공식 링크·`basis`(confirmed / preview / none)·`preview_from`(대표 공고 id·제목·공고일)·결과(eligible / likely / check / unlikely / ineligible / unjudged)·계층별 결과와 이유 |
| `POST /find/request-analysis` | `{key}` → 공고별 익명 건수 +1(누가 요청했는지 남기지 않음, 같은 요청 반복은 화면에서 한 번만) |

- 저장소에 닿지 않으면 등록 공고만으로 목록을 만들고 "실시간 목록을 잠시 불러오지 못했습니다"를 보인다(DB가 판정을 막지 않는다는 원칙 그대로).
- 수집이 24시간 넘게 멈추면 `stale` — 화면 위에 기준 시각과 안내.
- 수집 공고 읽기는 API 프로세스 안에서 5분 캐시(요청마다 DB를 읽지 않음).

### 화면 (Next.js `/find`)

1. **첫 화면 = 기본 자격조건**(1분 안팎, PRD 8절). 회원이면 대표 '내 조건'을 채워 두고 바로 목록. 저장 파일 불러오기 그대로.
2. **목록** — 위: 조건 요약(고치기)·기준 시각·거르기(지역 기본값 = 거주지 시·도, 임대/분양, 접수 중만).
   묶음: **지원 가능(확정) → 가능성 있음(예비) → 확인 필요 → 접힘: 어려움 · 판정 안 하는 사업**. 묶음 안은 접수 중 → 접수 예정, 마감 가까운 순.
   카드: 기관·사업·공고명·지역·접수기간(D-일)·결과·근거 출처(이 공고문 / 같은 사업 최근 공고)·공식 링크. 예비는 확정과 다른 표시(테두리·'예비' 글자).
3. **추가 질문** — "이것만 알려 주시면 N건이 더 판정됩니다"(정보 부족이 가장 많이 걸린 항목 1~2개, 지금의 `missing_fields` 재사용).
4. **공고 상세** — 확정: 지금의 계층별 판정·근거. 예비: 대표 공고 기준 판정·근거 + "공고문을 올리면 바로 확정"(재판소로, 공고 키 전달) · "분석 요청".
5. 지금의 전체 조건 흥신소(등록 공고 전부·지난 공고·What-if)는 목록 아래 "자세히 — 전체 조건으로 모든 공고 보기"로 남긴다.

### 운영 (F36)

- 운영자 검토 화면 '분석 대기 공고': 판정 틀 있음·분석 전 공고를 **접수 시작 가까운 순 → 요청 많은 순**, 공식 링크. 운영자가 공고문을 내려받아 올리면
  (기존 업로드 경로) 분석이 저장되고 F35로 바로 확정 판정.
- 지표(운영자 화면·수집 요약): 확정 판정 범위 = 마감 안 된 (등록 + 판정 틀) 공고 중 확정 판정 가능한 비율, 접수 시작일 기준 80% 목표.

### 개발 순서 (각 단계: 브랜치 → 시험·CI → 사용자 승인 후 병합·배포)

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| ②-1 | 예비 판정(`live_judge`) + 되짚어 보기(`eval_preview`) | 놓침 0(나온 틀은 '어려움' 끔), 틀별 보고표, 시험 |
| ②-2 | 수집 공고 ↔ 분석 잇기 + `GET /find/form`·`POST /find`·분석 요청 | API 시험(확정·예비·판정 안 함·저장소 없음·stale), 개인정보 저장 없음 시험 |
| ②-3 | 흥신소 첫 화면 개편(기본 조건 → 목록 → 상세) | Playwright PC·모바일, 회원 '내 조건' 바로 목록 |
| ②-4 | 운영자 분석 대기 공고·확정 판정 범위 지표 | 운영자 화면 시험 |
| ②-5 | SH 목록(서울시 주택포털 — 약관·구조 확인, 실패 감시) | 수집 시험, SH 공고가 목록에 |
| 3단계(선택) | LH 공식 첨부 주소 자동 분석 | 사용자 결정(robots) |

## 위험

- LH 응답에 접수기간·첨부 필드가 실제로 있는지 활용신청 뒤 가이드로 확인(없으면 상세 페이지 링크까지).
- 서울시 주택포털 구조가 바뀌면 SH 수집이 멈춘다 — 실패 감시.
- 운영 계정 전환은 심의가 있다. 1~3시간 주기면 트래픽 한도는 충분할 것으로 본다.
- (2026-11-10) 예비 판정을 확정으로 오해 — '지원 가능' 표현 금지·근거 출처 늘 표시·다른 표시. 예비가 공고를 잘못 숨김 — '어려움'도 접어서 보이고 놓침 0 기준.
- (2026-11-10) 분석 대기 공고가 쌓이면 목록 대부분이 예비 — 확정 판정 범위 지표로 매주 확인, 모자라면 3단계 결정.
