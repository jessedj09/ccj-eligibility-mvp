### 기존 기대값(EXPECTED) 변경 내역

- **P05 / N3 / 청년: `INELIGIBLE` → `NEEDS_INFO`.** P05는 `house_head_status`를 지정하지 않은
  프로필이다. 수정 전 코드는 이를 "세대주"로 추정해 (우연히 이 케이스에서는 결과가 같았지만)
  확정 `INELIGIBLE`을 냈다. 수정 후에는 이 정보 없이는 어떤 소득기준을 적용할지 알 수 없으므로
  `NEEDS_INFO`가 올바른 답이다. **"통과를 유지하려고 잘못된 기대값을 보존하지 않는다"는 작업
  원칙에 따라 EXPECTED를 고쳤다** — 이 변경 자체가 버그 5번의 재현·수정 증거다.
- 그 외 P01~P12는 새로 필수가 된 필드(`student_status`, `marriage_date`,
  `youngest_child_birth_date`)를 각 프로필의 기존 설정과 모순되지 않게 보강했을 뿐,
  소득/자산/가구원수 등 원래 검증 대상 값은 전혀 바꾸지 않았다(`src/profiles_data.py` 주석 참조).

## 3. 해석 쟁점과 `MANUAL_REVIEW` 처리 (MVP0.2 개정)

원문 해석이 갈리는 조건은 **임의로 통과/탈락시키지 않고** `MANUAL_REVIEW`(수동 확인 필요)로
분류한다. 사용자에게 정보를 더 물어도 해결되지 않는 것(=`NEEDS_INFO`와 다른 것)이라 별도
상태다. 구현 방식: 조건을 **여러 해석으로 각각 계산**해서(`resolve_interpretations`), 모든
해석이 같은 결과면 확정하고 갈릴 때만 `MANUAL_REVIEW`로 돌린다. 그래서 어떤 해석으로 봐도
결과가 같은 입력(예: 자산이 한도보다 한참 낮거나 높음)은 여전히 확정 판정이 나온다.
사유 코드: `AMBIGUOUS_SOURCE`(원문 표에 없는 조합/해석 갈림), `INPUT_INCONSISTENT`(가구원수와 혼인·자녀 입력이 서로 모순 — 입력 확인 필요), `SELF_REPORT_UNVERIFIED`(자기신고로만
처리하는 세부요건에 의존).

verdict 우선순위: **확정 불충족(INELIGIBLE) > 해석 미확정(MANUAL_REVIEW) > 정보 부족(NEEDS_INFO)
> 충족(ELIGIBLE)**.

### 정정 (MVP0.1 기록의 오류)

MVP0.1 대조표는 "N3 혼인기간 7년/6세이하 컷오프가 원문에 없고, N1의 하루 차이(2019.7.29 vs
7.30)가 일반화 가능한지 모른다"고 썼으나 **이는 틀린 설명이었다.** 하루 차이는 원문의 특이값이
아니라 만 나이 정의다: "6세 이하" = 아직 만 7세가 되지 않음 = 공고일 7년 전 날짜의 *다음 날* 이후
출생. 공식(`혼인=공고일-7년`, `자녀=공고일-7년+1일`)이 N1 리터럴 두 값을 정확히 재현함을
테스트로 확인했다(`test_cutoff_formula_reproduces_n1_literal_dates`).

- **MVP0.1의 N3 코드 오류 수정**: 자녀 컷오프를 혼인 컷오프와 같은 날짜(2019-08-19)로 둬서 공고일에
  **만 7세가 되는 아이(2019-08-19생)를 "6세 이하"로 통과**시키고 있었다. 이제 2019-08-20로 도출한다.
- N3에 남는 가정은 "N3도 N1과 같은 LH 표준 문구·만 나이 기준을 쓴다" 하나뿐이며, 같은 문구이므로
  위험이 낮다고 판단해 `MANUAL_REVIEW`가 아닌 확정 판정으로 두었다(Q3로 확인 권장).

### 출생자녀 가산 대상 자녀 수 — 엔진이 직접 계산 (MVP0.3에서 해결)

원문(N1 p.4 / N2 p.5 / N3 p.7 각주): "출산자녀는 '23.3.28. 이후 출산(입양·태아 포함)한 자녀.
기준일 이후 출산 자녀가 있는 경우에는 기준일 이전 출생한 기존 미성년자녀도 포함하여 최대 2자녀로
인정(단, 세대별 주민등록표 등재자에 한함)". 이제 사용자는 **자녀별 생년월일 목록**
(`children_birth_dates`)만 입력하고, 엔진이 공고별 공고일로 `bonus_child_count()`를 계산한다.
자녀 유무(`has_children`)와 막내 생년월일(6세 이하 요건)도 같은 목록에서 파생된다.

- 이후 출생(태아는 출산예정일) 1명 이상 → 기존 미성년(공고일 기준 만 19세 미만) 합산, 최대 2명.
- 이후 출생이 없으면 기존 미성년이 있어도 0명.
- 미성년 판단 기준일은 각 공고의 공고일(공고마다 결과가 달라질 수 있음 — 테스트로 확인).
- 이전 입력 방식(`young_child_count`)은 자녀 목록이 없을 때만 쓰이고, 목록이 있으면 목록이 우선한다.

**남은 가정(LH 확인 Q5)**: ① "기준일 이후"를 기준일 당일 출생 포함으로 읽음 ② 미성년 = 공고일
기준 만 19세 미만으로 읽음. 그리고 "세대별 주민등록표 등재 자녀만", "재혼 배우자의 전혼 자녀는
신청자와 같은 등본 등재 시만(N1 p.4)"은 사용자가 입력 단계에서 지켜야 하는 전제이며 엔진이
검증하지 못한다.

### 아직 미해결인 것
- 대학생 "부모 소득은 등본 등재 여부와 무관하게 포함", 청년 "해당 세대 범위"처럼 **가구원수와
  합산 대상을 사용자가 이미 올바르게 계산했다고 가정**하는 구조는 그대로다.

## 4. 지원 범위 밖으로 명시한 항목 (구현하지 않기로 결정)

- **사회초년생(N3-R5b) 세부요건 미검증**: "소득활동기간 5년 이내"의 정확한 계산(국민연금
  가입증명서·건강보험 자격득실확인서 대조, 재학/휴학 중 소득활동 기간 제외, 병역 기간 제외
  등)과 "퇴직 후 1년 이내 구직급여 수급자격", "예술인복지법상 예술활동증명"은 전부 서류 증빙이
  필요한 사실 확인이라 자동판정 대상이 아니다. `is_social_rookie`는 사용자의 자기신고 사실로만
  다룬다.
- **예비신혼부부의 "혼인으로 구성될 세대 전원 무주택"**: 기존 02-data-schema.md 한계를 그대로
  승계 — `home_ownership` 단일 필드로 단순화되어 있고 배우자 예정자 세대는 별도 조회하지 않는다.
- **대학생 소득 산정 시 "이혼 등으로 가족관계 단절된 경우 부양 부/모 소득 조회"**: 이 구현은
  사용자가 이미 올바른 부모(또는 부양자) 소득을 포함해 `monthly_income`을 입력했다고 가정한다.
  N2 p.6의 "신청자의 부모는 등본 등재 여부와 무관하게 항상 포함"이라는 규칙은 UI 안내 문구로만
  반영했다(계산 로직은 이미 합산값을 받는 구조라 별도 처리가 불필요).
- **접수기간·서류심사·경쟁 시 선정(순위/추첨/배점)**: verdict는 "필수조건 충족 여부"만
  판정한다. 접수 종료 여부, 순위 결정, 추첨 결과, 우선공급 배점(청약저축 납입횟수 등, 단
  `priority_scoring.py`로 별도 계산은 가능)은 이 계산기의 최종 자격판정에 포함되지 않는다 —
  Streamlit 화면 하단 "지원 범위" 안내에 명시했다.
- **N1/N2 주거약자용(17B/19B, 3-2 섹션) 서브타입**: 기존 02-data-schema.md 한계를 그대로
  승계 — 별도 물량이라는 사실만 문서화, 조건 리스트로 코드화하지 않음.

## 5. 완료 조건(필수조건 누락 시 ELIGIBLE을 반환하지 않는 설계)

`rule_engine.evaluate()`의 우선순위는 변경하지 않았다: **`failed`가 하나라도 있으면
`INELIGIBLE`, 없고 `unknown`이 하나라도 있으면 `NEEDS_INFO`, 전부 확인되고 전부 충족했을 때만
`ELIGIBLE`.** 이번 개정으로 새로 추가된 모든 조건(재학요건, 연령/사회초년생, 혼인기간/자녀요건,
세대주 정보, 자녀가산 적용 가구원수)은 이 우선순위에 그대로 편입되므로, "정보가 없어서 판정을
못 했는데 신청 가능하다고 나오는" 경로는 구조적으로 발생하지 않는다(§1의 버그 5·6·7이 바로 이
설계가 깨져 있던 사례였다).
